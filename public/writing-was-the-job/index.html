The profiler is a valid ranking instrument and an invalid sizing one.

It could not tell me how many milliseconds that thing cost. I used a ranking instrument to do sizing, and it gave me a number, and the number was garbage, and nothing in the tool told me so.

Thing one. Make it show its receipts.

If the failure mode is that everything sounds equally certain, then the fix is to stop letting everything sound equally certain.

Every statement an agent hands me is one of four things, and each one has a different failure cost, so each one gets labeled separately.

A CLAIM is a fact about our codebase. A CITE is a fact from outside it. A GUESS is inference, pattern-matching, recollection, "usually." An ACTION is something that changed state.

Flattened into one stream of confident prose, none of these can be trusted, because you can't tell them apart. Labeled, I can read a report in a third of the time and know exactly where to push.

No receipt, no claim. It gets downgraded to a guess.

And each type has a required receipt.

A CLAIM needs a file and a line number, or the exact command and its actual output. A CITE needs a URL fetched in this session or a test run in this session. A GUESS needs nothing, but it has to say out loud that it's a guess. An ACTION needs the command, the exit code, and how to reverse it.

The rule that makes the whole thing work is this. The type is set by whether a receipt is attached, not by how confident the statement feels. No receipt, no claim. It gets downgraded to a guess and marked as one.

And "I could not verify this" is a successful report. That's important. I had to say that out loud in the instructions, because the default behavior of these models is to produce an answer rather than admit a gap.

The cheapest one first, and it's the one I run most.

Same diff, three different models, from three different labs, each in a deliberately different information environment.

I ran this yesterday on a commit that had already shipped. The architecture leg ran out of time and returned nothing. The spec leg had no ticket to check against. The only leg that produced anything was the cold read — the handicapped one — and it came back with eleven findings, one of them critical.

The critical one: we had added a version three to our API by hand-copying the version two route block and changing one hook. Nothing enforces that the two stay in sync. Add a route to v2, forget to mirror it, and it is silently missing from the version everyone is actually on. That had been merged for a while.

And the reason I trust that finding is the line underneath it. Every finding it returns has a field called "first read" — what it assumed before it looked. On this one it wrote: I assumed v3 was generated from a shared list. It is a parallel hand-maintained block. It told me what it got wrong on the way to being right.

Then I merge the three reports, and the ranking signal is not severity. It's agreement. When two labs that share no training run independently flag the same line, that's real. When only one flags it, it's worth a look and it's not evidence.

I want to be precise about what this costs, because it isn't dollars. All three legs run on flat-rate plans. The cost is wall clock. I capped each leg at ten minutes, and I have the numbers from real runs: the two fast legs come back in one to seven minutes, and the architecture leg — the one with full repo context — takes eight, nine minutes. On a diff of about a hundred and fifty kilobytes it hit the cap and returned nothing at all.

So call it ten minutes a run, and I get two or three runs a week.

Which means I can't run it on every diff and stay in flow. So I gate it: only before something lands that touches shared surface area. API contracts, design tokens, anything more than one repo consumes. Never on a one-file diff.

Version one of the receipts rule was the simple one. No receipt, no claim, downgrade it to a guess. Clean. Obviously correct.

And it failed in a way I did not predict. The agents got very good at labeling things GUESS, and very comfortable there. Something that would have taken one grep to settle came back marked as a guess, correctly labeled and completely useless. I had traded confident wrong answers for honest shrugging.

So version two added the opposite pressure. If a tool already in your hand settles it in under a minute, run it, don't label it. And that overcorrected immediately. Agents started verifying throwaway asides. Every passing remark turned into a tool call. The turns got slower and no better.

Version three is version two with a bound on it: this only applies to statements another decision actually depends on. Passing remarks stay a guess and we move on.

That's three rewrites of one paragraph, and I only found each problem by watching real sessions fail. I could not have reasoned my way to version three from my desk. And the one on the slide back there, the "everyone knows minus two" rule, came from exactly this: two statements like that went through unlabeled in a live session, both were checkable in under a minute, and one of them was wrong in a way that would have shipped a bug.

So when you start doing this, expect your first instruction file to be wrong. Not because you wrote it badly. Because you cannot see the failure mode until you watch it happen.
